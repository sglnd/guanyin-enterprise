# 独立知识向量 PostgreSQL 的部署评估

当前企业版 hotfix.14 仍使用平台主库中的 pgvector，升级包没有独立向量数据库连接配置。不要仅复制一个 PostgreSQL 后修改控制台或 Worker 的 DATABASE_URL，这会使账号、空间、模型、权限及知识元数据指向不同实例。

## 何时适合独立实例

知识规模、检索并发或索引重建已经明显影响平台主库时，独立 PostgreSQL 实例配合独立 PVC、连接池及资源限额更有利于隔离负载。同一 PostgreSQL 实例中新建一个 database/schema 只提供逻辑隔离，CPU、内存和磁盘 IO 仍共用；如果实例仍在同一节点、同一物理磁盘，物理 IO 隔离也不完整。

小规模部署可以先共库，但需观察真实查询延迟、IO、连接数、索引与备份大小；合成分块功能测试不能代替生产压测。

## 建议的后续拆分边界（尚未实现）

- 平台主库继续保存账号、空间、库权限、绑定、文档与 Wiki 版本、发布状态、审计。
- 独立向量库存放向量及必要的分块/模型/版本标识，使用独立凭据、私网访问和连接池，不向浏览器开放数据库。
- 增加独立 VectorStore 接口及连接配置；目前 knowledge_chunks 与文档版本有外键，检索还会 JOIN 主库文档/知识库，必须改造，不能直接跨库沿用原 SQL。
- 接入检索前由主库计算授权库和发布版本白名单；查询后再次校验，确保撤权、删除或新版发布后不会返回过期的跨库结果。
- 两个数据库不再有单库事务，需要持久任务/outbox、幂等写入、发布版本切换及失败补偿；索引未准备好时不得切换为已发布，删除/撤权应由主库立即拒绝访问。
- 独立备份和重建机制；权限、原文、Wiki、向量恢复须按版本一致，不能恢复旧向量后直接放开所有访问。

这属于后续存储适配开发，不包含在本次已验证的共库发版路径中。知识库对空间的内部 API/MCP 入口可以保持，拆库不要求额外增加独立 MCP 网关。
